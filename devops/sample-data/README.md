# Sample import files

Two files for exercising **Import** in the UI by hand. Both were generated against the
reference data migration 0002 seeds — the country codes, departments, bands and currencies
in them are real rows, not plausible-looking strings — and both were run through
`app.services.importer.run_import` before being committed here, so what they do is known
rather than hoped.

| File | Rows | What it does |
|---|---|---|
| `employees-sample.csv` | 30 | Imports cleanly: 30 employees, 30 salaries. |
| `employees-with-errors.csv` | 10 | Fails validation with 7 errors and writes **nothing**. |
| `employees-10k.csv` | 10,000 | The size the brief names. Validates clean. **Read the warning below before importing it.** |

## The 10,000-row file

Generated by `python -m scripts.seed --csv <path>` — the same generator that builds
the database seed, so the two describe the same company rather than drifting apart.
Codes are `BULK-000000`…`BULK-009999`, chosen not to collide with `SEED-` or `ACME-`.

**Preview is fast; the import is not.** Previewing all 10,000 rows takes ~0.2 s. The
import itself takes **~72 seconds**, because each row goes through the employee and
salary services individually — roughly 50,000 round trips. That is past most default
HTTP timeouts, so a browser upload may give up before the server finishes, and the
import is still running when it does. [ADR-0004](../../plan_doc/adr/0004-synchronous-import-no-job-queue.md)
has the measurement and what would fix it.

Use it to exercise the **preview** screen at full size. To get 10,000 employees into
the database for testing the list and dashboard, skip the import and seed directly —
it takes 6.9 s:

```bash
cd backend
python -m scripts.seed                 # 10,000 employees, ~18,700 salary rows
python -m scripts.seed --clear         # remove them again
```

## Using them

1. Start the stack: `cd devops && docker compose up -d --wait`
2. Open http://localhost:5173 and sign in.
3. **Import** → choose a file → upload.

`employees-sample.csv` covers ten countries and ten currencies, including JPY (no minor
units — whole yen) and the three-decimal cases the schema stores at `NUMERIC(14,3)`. Band
`L1`–`L7` and the department names are the seeded ones.

Employee codes are `ACME-1000`…`ACME-1029`, chosen not to collide with `SEED-` codes from
`backend/scripts/seed.py`. **Re-uploading the same file a second time fails** on duplicate
employee codes — which is correct behaviour, not a bug. To re-test, either delete those
rows or edit the codes.

## The error file

It is a copy of the first ten valid rows with one deliberate mistake of each kind, so the
error report in the UI has something to show:

| Row | Field | Error |
|---|---|---|
| 3 | `currency` | Unknown currency: XYZ. |
| 5 | `hire_date` | Use YYYY-MM-DD, got '01/04/2024'. |
| 6 | `amount` | Must be positive, got -5000. |
| 7 | `country_code` | Unknown country: ZZ. |
| 8 | `department` | Unknown department: Teleportation. |
| 9 | `employee_code` | Required. |
| 10 | `employee_code` | Duplicate of row 2: ACME-1000 appears twice. |

Row numbers are the line numbers in the file as a spreadsheet shows them — the header is
row 1 — so a user can go straight to the row that is wrong.

The point of this file is the all-or-nothing rule: three of its ten rows are perfectly
valid and **none of them is imported**. A half-applied payroll file is worse than a
rejected one, because reconciling it is manual work (see
[ADR-0004](../../plan_doc/adr/0004-synchronous-import-no-job-queue.md)).

## Columns

Required: `employee_code`, `first_name`, `last_name`, `country_code`, `department`,
`job_title`, `hire_date`, `amount`, `currency`, `effective_from`.
Optional: `email`, `band`.

The Import page offers a template download with exactly these columns, so this file is a
convenience rather than the only way to get a valid header row.
